# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Qué es este proyecto

Babylon es un sistema de gestión académica para un instituto de inglés real (Babylon English Institute, ~130 alumnos, 5 profesores), y a la vez el Proyecto Final de Carrera de Agustín Luconi (Práctica Profesional III). Cuatro roles con acceso estrictamente diferenciado: **Administrador** (acceso total), **Secretario** (legajos, cuotas/pagos, observaciones), **Profesor** (solo sus propios cursos), **Padre/Madre/Tutor** (solo lectura de sus propios hijos, privacidad absoluta entre alumnos).

Es un monorepo con `server/` (API) y `client/` (SPA) totalmente independientes — no hay código compartido entre ambos.

## Comandos

Se quedó en TS 6.0.3, la última versión "clásica" (mismo motor de tipos que la 5.x) y la última con la que el ecosistema de lint funciona. Retomar la 7 cuando `typescript-eslint` la soporte. Dos opciones de tsconfig quedaron removidas en ambas versiones (6 y 7): `baseUrl` (TS5102, ya no se lee — alcanza con `paths` solo, Vite resuelve el alias `@/*` por su cuenta vía `resolve.alias` en `vite.config.ts`, no depende de esto) y `moduleResolution: "Node"`/`node10` (TS5108, eliminado — el server no declara `moduleResolution` explícito, TS lo infiere de `module: "CommonJS"`).

**Prisma 6 (desde 2026-09-22; antes 5; NO se llegó a la 7)**: la 5→6 se hizo (sin cambios de código — el schema no usa ninguna de las cosas que rompe: relaciones m2m implícitas, campos `Bytes`, `fullTextSearch`, `$use()`). **La 6→7 se evaluó y se decidió posponerla a propósito** (decisión del usuario, no una limitación técnica encontrada) — a diferencia de todas las demás actualizaciones de esta tanda, Prisma 7 no es un cambio de versión de rutina: exige convertir **todo el server** a ESM (`"type": "module"`, con todo lo que implica: extensiones `.js` en cada import relativo, revisar que `bcrypt`/`jsonwebtoken`/`cors`/`express` sigan andando en ESM), reemplazar cómo se instancia `PrismaClient` por un adaptador de driver (`@prisma/adapter-pg`), y mover el cliente generado a una carpeta nueva (actualizando los imports en los ~13 `*.repository.prisma.ts`). Si se retoma, tratarla como su propia migración, no como un paso más de una lista de actualizaciones.

**Tailwind CSS 4 (desde 2026-09-21; antes 3.4)**: no hay `tailwind.config.ts` ni `postcss.config.js` — la configuración vive en `client/src/index.css` (`@import 'tailwindcss'`, bloque `@theme`) y Tailwind entra por el plugin `@tailwindcss/vite` (`vite.config.ts`). Se migró con `@tailwindcss/upgrade` y se verificó comparando 39 capturas antes/después (36 idénticas al píxel; el resto, diferencias menores explicadas). Particularidades de v4 que ya causaron regresiones y hay que recordar: (1) `!` de importante va al final (`mb-0!`) y **anula el `margin-bottom` que `space-y-*` aplica** — no ponerlo en elementos dentro de un `space-y-*`; (2) `space-y-*` ahora usa `margin-bottom` sobre los hijos que no son el último, así que **se suma** a un `mt-*` del hijo (en v3 lo pisaba) y cuenta hijos ocultos por CSS (`md:hidden`); (3) el interlineado de `text-sm`, etc. ya no es fijo: se restauraron los valores de v3 en `@theme` (`--text-*--line-height`) para que las tablas no cambien de alto; (4) `rounded` → `rounded-sm`, `shadow-sm` → `shadow-xs`, `outline-none` → `outline-hidden`; (5) CSS propio sin capa (`.input`, `.label`, `.btn-*`…) le gana a las utilidades de Tailwind (que están en `@layer`) salvo que estas usen `!`. `tailwind-merge` es 3.x (entiende los nombres de v4). ## Arquitectura — regla central: 100% feature-first

**Nunca crear carpetas de nivel superior `domain/`, `data/` o `presentation/`.** La organización es por feature de negocio, no por capa técnica:

- **`core/`** (en ambos proyectos) contiene *solo* lo transversal a todos los módulos: interfaces genéricas, errores de dominio, middlewares, conexión a la base de datos, utilidades sin estado. Nunca lógica de negocio de un módulo específico.
- **`modules/`** (server) / **`features/`** (client): una carpeta por feature de negocio. Cada carpeta trae **todas** sus capas juntas en archivos separados, no en subcarpetas por tipo.

### Anatomía de un módulo de server (ej. `modules/alumnos/`)

| Archivo | Responsabilidad | Regla estricta |
|---|---|---|
| `*.entity.ts` | Entidad pura | Jamás importa Express, Prisma, ni ninguna librería externa — solo tipos de `core/ports.ts` si corresponde (ej. `Rol`) |
| `*.schema.ts` | Validación con Zod | Define el input de cada caso de uso |
| `*.repository.ts` | Puerto (interfaz) | Extiende `Repository<T, ID>` de `core/ports.ts` |
| `*.repository.prisma.ts` | Adaptador real | Implementa el puerto con Prisma (`PrismaClient` inyectado por constructor). Todos los métodos aceptan un `tx?: unknown` opcional al final — ver "UnitOfWork" para por qué |
| `*.service.ts` | Casos de uso / reglas de negocio | Recibe el repositorio **por constructor** (inyección de dependencias), nunca lo instancia. Lanza errores de `core/errors.ts`, nunca códigos HTTP |
| `*.controller.ts` | Única capa que conoce HTTP | Traduce request/response; los errores de dominio los traduce el `errorHandler` central, no el controller |
| `*.routes.ts` | Definición de rutas Express del módulo | |

`container.ts` (en `server/src/`, no dentro de ningún módulo) es el **único** lugar donde se decide qué implementación de repositorio recibe cada service. Ningún otro archivo debe instanciar un repositorio directamente. **Los `*.repository.fake.ts` (adaptador en memoria) se usaron desde FASE 2 hasta la migración a Prisma (2026-08-01) y ya no existen** — se eliminaron junto con `FakeUnitOfWork` en cuanto quedaron sin ningún consumidor (mismo criterio de "no dejar código muerto" ya aplicado antes con el endpoint individual de asistencia). Si en algún momento se agrega un test runner y hacen falta test doubles, se reescribirían desde cero con ese propósito explícito, no resucitando los viejos.

### Convención de nombres de módulo/entidad

La carpeta del módulo lleva el **plural de la entidad principal (agregado raíz)**, no un nombre genérico de la feature. Las entidades secundarias viven en el mismo módulo con su propio nombre:

- `cuotas/` → principal `Cuota`, secundaria `Pago`
- `cursos/` → principal `Curso`, secundaria `Horario`
- `calificaciones/` → principal `Calificacion`, secundarias `Evaluacion` y `NotaCierre`
- `chats/` → principal `Chat`, secundaria `Mensaje`
- `observaciones/` → principal `Observacion`, secundaria `CategoriaPersonalizada`

Las entidades secundarias normalmente no tienen su propio `*.repository.ts` — se gestionan a través de métodos extra en el repositorio de la entidad principal (ej. `CuotaRepository.registrarPago(pago)`).

**`CategoriaPersonalizada` (scoping por curso, mismo comportamiento que `Evaluacion`)**: además de las 4 categorías predefinidas (`academico`, `comportamiento`, `felicitacion`, `administrativo`), un profesor puede crear categorías propias para un curso puntual (`POST /api/observaciones/categorias`, ownership validado por `verificarDuenoDelCurso`). `Observacion.categoria` es `string` (no un enum) porque guarda tanto el literal predefinido como el `id` de una `CategoriaPersonalizada`; `ObservacionService.crearObservacion` valida que, si no es una de las 4 predefinidas, exista una `CategoriaPersonalizada` con ese `id` cuyo `cursoId` coincida con el curso del alumno — si no, `ValidationError` (400). La categoría creada por un profesor **no se comparte** con otros cursos ni otros profesores.

### Errores de dominio (`core/errors.ts`)

`DomainError` es abstracta; toda subclase declara su propio `statusCode`. El `errorHandler` central (`core/middlewares/errorHandler.ts`) traduce cualquier `DomainError` a HTTP automáticamente — los controllers solo hacen `throw`, nunca `res.status(...)` para errores de negocio, y ni siquiera necesitan `try/catch`: **Express 5** reenvía nativamente a `next(err)` cuando un handler async rechaza una promesa (`express-async-errors`, que hacía esto en Express 4, se sacó en la migración a Express 5 — dejó de funcionar porque parcheaba un archivo interno, `express/lib/router/layer`, que cambió de lugar en la v5; el paquete además quedó redundante).

| Clase | HTTP | Cuándo |
|---|---|---|
| `EntityNotFoundError` | 404 | El recurso no existe |
| `ConflictError` | 409 | Estado inconsistente (DNI duplicado, cuota ya pagada, autorización ya aceptada) |
| `ValidationError` | 400 | Input inválido más allá de lo que ya cubre Zod |
| `AuthenticationError` | 401 | Credenciales inválidas (login) |
| `AuthorizationError` | 403 | El usuario autenticado no es dueño del recurso (profesor sobre un curso ajeno, padre sobre un alumno ajeno) |
| `DemasiadosPedidosError` | 429 | Demasiados pedidos seguidos de la misma cuenta (ej. reenviar el enlace de verificación del email) |
| `ServicioNoDisponibleError` | 503 | Un servicio externo del que depende el pedido (el servidor de correo) no respondió: se puede reintentar |

### Autenticación y roles

`Rol` (`"admin" | "secretario" | "profesor" | "padre"`) vive en `core/ports.ts`, no en `modules/usuarios` — `core/` no puede depender de `modules/*`, pero `authMiddleware.ts` (transversal) necesita ese tipo para tipar `req.auth.rol`.

- `authMiddleware` verifica el JWT y agrega `req.auth = { sub, rol, sesionId }`.
- `requireRole(...roles)` es un guard de nivel de ruta para chequeos de rol genéricos.
- **Sesiones por dispositivo** (`Sesion`, entidad secundaria de `usuarios/` con su propio `SesionRepository`): cada login crea una fila (dispositivo deducido del `User-Agent` con `core/dispositivo.ts`, IP, inicio, último uso, vencimiento) y el token lleva su id (`sid`; no hay claim `v`). `authMiddleware` valida **en cada pedido con una sola consulta** (validador inyectado por `container.ts` con `configurarValidadorDeSesion(crearValidadorDeSesion(sesionRepository))`, porque `core/` no puede importar `modules/`; sin validador falla cerrado): la sesión existe, es de esa cuenta (`sub`), no está cerrada (`cerradaEn`), no venció (`expiraEn`) y la cuenta está activa; si no, 401, y también para un token sin `sid` (los emitidos antes de las sesiones dejaron de valer). `req.auth` trae `sesionId`. Se cierran sesiones al **cerrar sesión** (`POST /api/auth/logout`: el token deja de valer en el servidor), al **cambiar la contraseña** desde "Mi cuenta" (las demás; la actual sigue abierta), al **recuperarla** y al **desactivar** la cuenta (todas, por cualquier camino: `UsuarioService.cambiarEstado` o la ficha del profesor); reactivar una cuenta no las revive (hay que volver a iniciar sesión). **El último uso** (`ultimoUsoEn`) no se escribe en cada pedido: el validador lo registra como máximo cada 5 min con una actualización condicional que no se espera, y también al iniciar sesión y en `GET /api/auth/sesiones`. **Los cambios sobre `Usuario` usan `actualizarParcial` (solo los campos que cambian), no `update` con la fila entera**: así dos cambios simultáneos (una contraseña nueva y un cambio de estado, por ejemplo) no se pisan.
- **Retención de sesiones**: las terminadas (cerradas o vencidas) se conservan 90 días y la tarea diaria de las 03:00 (`core/tareaDiaria.ts`, `programarTareaDiaria`, compartida con las cuotas) las borra, de cualquier cuenta; las activas nunca se tocan. **Carreras entre login y cambios de la cuenta**: la sesión del login se crea dentro de una transacción con `bloquearCuenta` y releyendo la cuenta (si el administrador cambió la contraseña o se desactivó la cuenta mientras corría bcrypt, el login falla); editar una cuenta (`actualizarCuenta`), `cambiarEstado` y la ficha del profesor toman el mismo bloqueo. **Tope de 10 sesiones abiertas por cuenta** (`MAX_SESIONES_ACTIVAS`): al iniciar una nueva en el tope se cierra la menos usada.
- **Cuentas administradas por el administrador (sin correo)**: **solo el administrador crea cuentas, asigna contraseñas y las cambia**; nadie cambia ni recupera su propia contraseña ni su email (quien la olvida se la pide al administrador) y el sistema **no envía correos** (no hay `Mailer`, `SMTP_*`, `APP_URL` ni `nodemailer`). Las cuentas son `activo`/`inactivo` (ya no existe `pendiente`) y no hay enlaces por correo ni `TokenCuenta`. **Las altas de fichas no crean cuentas**: `POST /api/padres`, `POST /api/profesores` y la inscripción crean solo la ficha (`PadreService`/`ProfesorService.crearFichaEnTransaccion`); el `email` de una ficha es un dato de contacto y el de una ficha con cuenta es siempre el de la cuenta. `UsuarioService` (solo `admin`): `listarSinCuenta` (responsables y profesores activos sin `usuarioId`), `buscarPorEmail`, `crearCuenta` y `actualizarCuenta` (ver "Cuentas: crear y editar" más abajo). Dos pedidos con el mismo email se hacen de a uno (`bloquearCuenta("email:<email>")`). Las contraseñas cumplen `passwordNueva` (mínimo 8, máximo 72 bytes, no solo espacios).
- **Sesión por pestaña** (`sessionStore`, Zustand `persist` sobre `sessionStorage`, clave `babylon-session`): cada pestaña tiene su propia sesión, así dos pestañas del mismo navegador pueden estar con cuentas distintas. Recargar la conserva; cerrar la pestaña la termina; una pestaña nueva arranca sin sesión (duplicar una pestaña copia su `sessionStorage`: comparte la misma sesión del servidor, no abre otra). **No existe "Mantener sesión iniciada"**: el token dura `JWT_EXPIRES_IN` (8h) y se borró `recordarme`/`JWT_EXPIRES_IN_RECORDAR`. Un token que una versión anterior dejó en `localStorage` se descarta al cargar. Ante un 401 con sesión, `apiClient` borra el almacenamiento (`persist.clearStorage`, no `cerrarSesion`: eso dispararía antes la redirección de `ProtectedRoute` sin el aviso) y recarga en `/login?motivo=sesion-vencida`.
- **Límites de pedidos** (`core/middlewares/limitesDePedidos.ts`, `express-rate-limit`, en memoria — alcanza con un solo servidor): login fallido 5 cada 15 min por IP+email y 20 por IP (los exitosos no cuentan). Detrás de un proxy hay que configurar `TRUST_PROXY` con la **cantidad de proxies delante** (normalmente `"1"`): sin eso todos compartirían la IP del proxy y 20 intentos fallidos en total dejarían a todo el instituto sin poder entrar durante 15 min; `"true"` se rechaza al arrancar porque confiaría en el `X-Forwarded-For` que manda el propio cliente y permitiría esquivar los límites. **Los emails de cuenta se guardan normalizados** (trim + minúsculas, en `PrismaUsuarioRepository.create/update`) y `findByEmail` busca por igualdad exacta: no usar `mode: "insensitive"` de Prisma, que genera `ILIKE` donde `_` y `%` son comodines. El login tarda lo mismo con una cuenta que existe que con una que no (sin cuenta se compara igual contra un hash de relleno, `HASH_DE_RELLENO`): el tiempo no delata qué emails están registrados.
- Los chequeos de **propiedad sobre un recurso específico** (¿es este profesor dueño de este curso puntual?, ¿es este padre dueño de este alumno puntual?) van **dentro del service**, no en middleware, porque dependen de datos — lanzan `AuthorizationError`.

### Cuentas con más de un rol (ej. dueño del instituto que también dicta clases)

`Usuario.roles: Rol[]` (plural) — una cuenta puede tener habilitado más de un rol. El **JWT sigue llevando un solo rol activo por sesión** (`{ sub, rol, sid }`, singular) — este es el punto clave de la decisión: `requireRole`, todos los controllers, y el `Rol` del client **no cambiaron nada**, porque lo único que varía es cómo se llega a tener ese rol único en el token.

`UsuarioService.autenticar` devuelve una unión discriminada por `requiereSeleccionRol`:
- Si `usuario.roles.length === 1`: sesión completa de una (`{ requiereSeleccionRol: false, token, usuario }`), como siempre.
- Si tiene más de uno y el body de `POST /api/auth/login` no manda `rolElegido`: devuelve `{ requiereSeleccionRol: true, rolesDisponibles: Rol[] }` — **sin token todavía**.
- El client vuelve a llamar al mismo endpoint con las mismas credenciales + `rolElegido` (no hace falta un token intermedio ni estado en el server entre los dos pasos — es stateless). Si `rolElegido` no está en `usuario.roles`, `ValidationError` (400).

`LoginPage.tsx` maneja el flujo en dos pasos: guarda las credenciales en estado local tras el primer submit, y si la respuesta pide selección de rol, muestra un botón por cada rol disponible (`ROL_LABELS` en `features/auth/types.ts`, reusado también en `AppLayout`) que reenvía las mismas credenciales + el rol elegido.

`container.ts` siembra a Silvana Linares con `roles: ["admin", "profesor"]` (además de su `Padre`/`Profesor` real correspondiente) como ejemplo de cuenta multi-rol para probar el flujo.

### UnitOfWork (operaciones atómicas multi-registro)

`UnitOfWork<TContext>` (`core/ports.ts`) es genérico — no sabe nada de Prisma. `PrismaUnitOfWork` (`core/adapters/`) lo implementa con `Prisma.TransactionClient` real (`this.prisma.$transaction(work)`). Se usa para operaciones que tocan múltiples registros a la vez: `CuotaService.registrarPago` (pagar varias cuotas), `PadreService.crearPadre`/`ProfesorService.crearProfesor` (alta de Usuario + entidad), `AsistenciaService.registrarAsistenciaMasiva` y `CalificacionService.cargarCalificaciones` (cargar notas de toda una nómina en una sola operación "todo o nada" — esta última además valida que cada `alumnoId` pertenezca a la nómina del curso de la evaluación, `ValidationError` si no). **Las notas de cierre se cargan y se publican por lote** (`CalificacionService.cargarNotasCierre` / `publicarNotasCierre`, un solo pedido y una sola transacción para todo el curso, todo o nada). Antes era un `POST` por alumno con `Promise.all`; con los avisos (subproyecto 3a) cada pedido abría su propia transacción con una sincronización completa bajo el mismo bloqueo, y con pocas conexiones a la base algunos alumnos podían quedar sin guardar. Por lote hay una sola sincronización y un único anuncio. **No existe un `registrarAsistencia` individual** — existió brevemente (uno de los 5 casos de uso críticos originales de FASE 2) pero se eliminó al agregar la versión masiva porque quedó sin ningún consumidor y sin ninguna capacidad que la masiva (con un array de un solo registro) no cubriera ya — evitar mantener dos caminos para el mismo caso de uso sin una razón de negocio real detrás.

**Cómo el `tx` llega hasta el repositorio (clave para que la atomicidad sea real, no solo de intención)**: `Repository<T, ID>` (`core/ports.ts`) declara un parámetro extra `tx?: unknown` en los 5 métodos genéricos, y cada `*.repository.ts` propio hace lo mismo en sus finders/writers a medida (`findByAlumnoId(id, tx?)`, `registrarPago(pago, tx?)`, etc.). Es `unknown` **a propósito** — el puerto no puede importar `Prisma.TransactionClient` (rompería que server/módulos no dependan del adaptador concreto). Cada service que usa `unitOfWork.runInTransaction(async (tx) => { ... })` reenvía ese `tx` a **todas** las llamadas al repositorio dentro del callback (lecturas incluidas, no solo escrituras — necesario para que las verificaciones de conflicto vean el estado dentro de la misma transacción). `PrismaXxxRepository` internamente hace `(tx as Prisma.TransactionClient | undefined) ?? this.prisma` para usar la transacción activa si la hay, o el cliente normal si no. Este patrón se agregó recién al migrar a Prisma real (2026-08-01) — antes, con Fake, nadie pasaba `tx` a ningún lado porque no hacía falta (no había transacción real detrás); si se agrega un nuevo flujo con `UnitOfWork`, **no alcanza con envolver el código en `runInTransaction`** — hay que acordarse de pasar `tx` a cada llamada al repositorio dentro del callback, o la "transacción" no protegerá nada de verdad.

**Verificado que el rollback es real** (no solo estructurado para serlo): con dos alumnos en un curso, se mandó un `POST /api/asistencia/masiva` con `registros: [alumnoNuevo, alumnoConAsistenciaYaRegistrada]` — el segundo dispara `ConflictError` (409), y se confirmó con una consulta directa a Postgres que el primero **tampoco** quedó guardado (`SELECT COUNT(*) FROM "Asistencia"` no cambió). Con la Fake anterior esto no se podía garantizar (quedaba documentado como limitación conocida); con Prisma + `$transaction` ya es una garantía real del motor de base de datos, no una intención del código.

### Reglas de negocio transversales (viven en el `service`, no en el frontend)

- Descuento del 10% a partir del segundo hijo del mismo padre: `Alumno.aplicaDescuentoHermanos` se calcula en `InscribirAlumno` contando hermanos activos con el mismo `padreId`.
- Autorización de imagen: solo el padre dueño del alumno, una sola vez (`DocumentoService.autorizarImagen`); revocarla o pasarla a manual es exclusivo de Admin/Secretario.
- Un profesor solo opera sobre sus propios cursos (`AsistenciaService.registrarAsistenciaMasiva` valida `curso.profesorId`).
- Un padre solo ve datos de sus propios hijos.
- Calificaciones/notas de cierre en estado "borrador" nunca visibles para el rol Padre.

### Patrón `Crear<Padre|Profesor>`: alta de Usuario + entidad en una transacción

`PadreService.crearPadre` y `ProfesorService.crearProfesor` crean el `Usuario` (con password hasheada) y la entidad (`Padre`/`Profesor`) vinculada por `usuarioId`, ambos dentro de `unitOfWork.runInTransaction(...)` — es el mismo patrón que `CuotaService.registrarPago`, reutilizado para altas que tocan dos repositorios a la vez. Cada uno valida que el email no esté usado (`UsuarioRepository.findByEmail`) y que el DNI no esté duplicado antes de crear nada.

`AsistenciaController` y `DocumentoController` ya **no** usan `req.auth.sub` directamente como `profesorId`/`padreId` (esa simplificación de FASE 3/4 quedó resuelta en FASE 5): ahora llaman a `ProfesorService.buscarPorUsuarioId` / `PadreService.buscarPorUsuarioId` para resolver la entidad real antes de invocar el service correspondiente.

### Cuentas: crear y editar (solo el administrador)

- **Crear** (`POST /api/auth/cuentas`, `crearCuentaSchema`): `{ email, password?, nombre?, roles[], padre?, profesor? }`. `padre`/`profesor` van si y solo si el rol está en `roles` y son `{ fichaId }` (una ficha sin cuenta) o `{ nueva: {…} }` (se crea la ficha en la misma transacción, con el email de la cuenta). **Si el email ya es de una cuenta no falla: le vincula la ficha y le agrega el rol**, sin tocar su contraseña ni su nombre (`vinculada: true`); 409 si esa cuenta ya tiene ficha de ese tipo o la ficha ya tiene cuenta. Sin cuenta previa, la contraseña es obligatoria. `GET /api/auth/sin-cuenta` y `GET /api/auth/usuarios/por-email?email=` (para avisar antes de guardar) completan el circuito (`por-email` trae también el `estado`: el modal avisa si la cuenta está desactivada y que seguirá así). Los endpoints `POST /api/auth/secretarios|administradores` ya no existen: administradores y secretarios se crean con `crearCuenta`. **Concurrencia:** `crearCuenta` sobre una cuenta existente toma su bloqueo (y el de `email:<email>`) y, como cambia sus roles, **cierra sus sesiones** (motivo `roles-cambiados`, salvo la del propio administrador); quitar el rol `admin` o desactivar a un administrador toma el bloqueo global `BLOQUEO_DE_ADMINISTRADORES` y cuenta los otros administradores activos (`contarOtrosAdminsActivos`, pura) para que dos administradores no se quiten el acceso a la vez y el sistema nunca quede sin uno; editar el email desde la cuenta y desde la ficha a la vez respeta el orden de bloqueos (cuenta primero: `actualizarPadre` relee la ficha para saber su cuenta) y `PrismaUsuarioRepository` solo traduce P2002/P2025 (cualquier otro error de la base se propaga, no es un 404).
- **Editar** (`PATCH /api/auth/usuarios/:id`, `actualizarCuentaSchema`, solo se escribe lo que vino): `nombre` (en una cuenta con ficha de padre o profesor se cambia desde la ficha: 400), `email` (único, 409; también cambia el de cada ficha vinculada, y al revés: editar el email de la ficha cambia el de la cuenta, `PadreService`/`ProfesorService`), `password` y `roles`. Cambiar la **contraseña** o los **roles** cierra todas las sesiones de esa cuenta (`sesiones.cerradas`, motivos `contrasena-cambiada` y `roles-cambiados`), salvo la desde la que se hace si el administrador se edita a sí mismo. Reglas de roles (`usuario.roles.ts`, pura): al menos un rol; un administrador no se quita su propio `admin`; el sistema nunca queda sin un administrador activo. Agregar `padre`/`profesor` vincula una ficha (como al crear); quitarlo la **desvincula** (`desvincularUsuario`: la ficha, sus alumnos y sus cursos no se tocan; vuelve a "Sin cuenta"). Al quitar un rol se **borran los avisos de ese rol** de la cuenta (`cuenta.cambio` con `rolesQuitados`; privacidad entre familias). No hay "borrar cuenta": retirar un acceso es desactivarla (`PATCH …/estado`). **Ficha ↔ cuenta:** editar el nombre o el email de la ficha de un responsable también los cambia en la cuenta (y el email, en la ficha de profesor de la misma cuenta, si la hay); el **estado** de la ficha de un profesor solo pasa a la cuenta si el pedido lo cambia y la cuenta es **solo de profesor** (una cuenta con más roles no se desactiva por desactivar la ficha: se hace desde Usuarios); editar otros datos de la ficha nunca toca el estado de la cuenta.
- **Cliente** (`features/usuarios/`): `UsuariosPage` con pestañas "Cuentas" y "Sin cuenta" (`?pestana=sin-cuenta`), `CrearCuentaModal` (desde "Crear usuario" para cualquier rol, varios a la vez, o desde "Crear cuenta" de una fila de Sin cuenta, con el email de la ficha autocompletado y el aviso "ese email ya tiene cuenta"), `EditarCuentaModal` (lápiz por fila; confirmación al quitar un rol atado a una ficha), `SelectorDeFicha` y `CampoPassword` (con ojito; no hay botón de generar contraseña).

### Avisos guardados y en tiempo real (subproyecto 3a)

**Tablero de anuncios** (`core/eventos.ts`): los services publican lo que pasó (`anuncios.publicar("cuotas.cambiaron", datos, tx)`) y otros módulos se suscriben, sin conocerse. Dos momentos: `alPublicarse` corre **dentro** de la transacción con el mismo `tx` (si falla, la operación entera se deshace) y `alConfirmarse` corre **después de confirmar** (`core/alConfirmar.ts`: `PrismaUnitOfWork` registra cada transacción y corre lo pendiente al confirmar; si se deshace, se descarta; si falla, queda en el log). Cada módulo declara sus anuncios en `<modulo>.eventos.ts`; `src/eventos.ts` (solo tipos) los junta en `EventosDelSistema` y `container.ts` arma el tablero. Los services reciben `anuncios: Publicador<…> = sinAnuncios()` como último parámetro (los scripts viejos que los construyen sin tablero siguen andando). **Regla:** publicar siempre dentro de la transacción de la operación y pasando `tx` (por eso `crearEvaluacion`, `publicarEvaluacion`, `cargarNotasCierre`, `publicarNotasCierre`, `crearObservacion`, las escrituras de documentos, `crearCurso` y `marcarVencidas` pasaron a usar `UnitOfWork`).

**Módulo `notificaciones/`** (ahora con entidad `Notificacion` y `NotificacionDesactivada`):
- Catálogo en `notificacion.tipos.ts`. De estado: `cuotas_vencidas` y `documentacion_pendiente` y `datos_incompletos` (agrupados, para admin/secretaría), `evaluacion_proxima` (hoy a +7 días), `asistencia_pendiente` (clases de los últimos 7 días sin asistencia, la de hoy solo si ya empezó, solo meses lectivos), `notas_sin_publicar`, `cierre_sin_publicar`, `cuota` (padre: por vencer ≤5 días y vencida son la misma fila) y `documentacion_hijo`. De evento (una vez por clave): `nota_publicada` (también si se carga una nota en una evaluación ya publicada), `cierre_publicado` (la clave lleva el momento de publicación: republicar avisa otra vez) y `observacion_nueva`.
- Destinatarios: solo cuentas `activo`, por rol (una cuenta multi-rol tiene avisos separados). Todo acceso filtra por `usuarioId` **y** `rol` de la sesión.
- **Criterio único por tipo** (`notificacion.criterios.prisma.ts`, lectura cruzada sobre Prisma como `reportes/`). Cada anuncio solo pide sincronizar los tipos afectados (`notificacion.suscripciones.ts`); se sincroniza **el tipo completo** con un bloqueo por tipo (`pg_advisory_xact_lock`), así dos operaciones simultáneas no chocan. Reglas en `notificacion.reconciliar.ts` (pura): se crea lo esperado, se reabre lo resuelto que vuelve a darse, vuelve a "no leído" si el `nivel` sube (cuota vencida, el número del agrupado crece) y se resuelve lo abierto que ya no corresponde (todo junto, en una sola sentencia: `resolverVarios`). El `recurso` se compara con las claves ordenadas (jsonb las reordena). Apagar una preferencia toma el mismo bloqueo del tipo. `PrismaUnitOfWork` da **20 s** a cada transacción (Prisma trae 5 s): activar un ciclo o reactivar una cuenta recalcula todos los tipos dentro de la operación.
- Preferencias: `NotificacionDesactivada` (que exista la fila = apagado). Apagar borra los avisos de ese tipo (también del historial); encender sincroniza en el momento.
- `iniciarAvisosPeriodicos` (`notificacion.scheduler.ts`): al arrancar y a las 03:00, revisión completa de los tipos de estado y limpieza (se borran los avisos con más de 30 días desde su última actualización, salvo los de estado abiertos); cada 15 minutos, `asistencia_pendiente` (`programarTareaPeriodica` en `core/tareaDiaria.ts`).
- El aviso guarda de qué recurso trata, nunca una dirección: el client la arma según el rol (`features/notificaciones/rutas.ts`).

**Conexión en vivo** (`GET /api/tiempo-real`, `core/tiempoReal.ts`, SSE): una por sesión (si se abre otra, la anterior recibe `reemplazada`), latido cada 25 s, corte al vencer el token y revalidación de la sesión cada 5 min; 10 aperturas por minuto por sesión (`limiteTiempoReal`, 429). Se abre con el encabezado `Authorization` y la validación de siempre: **nunca con el token en la dirección**. Solo viajan señales sin datos personales: `listo` (`{ version }`, la del servidor: ver "Pantallas al día"), `notificaciones` (`{ noLeidas }`), `chat` (`{ chatId }`, ver "Chat en vivo"), `cambio` (qué dato cambió, ids y quién: ver "Pantallas al día"), `reemplazada`, `sesion-cerrada` (`{ motivo }`). Al (re)conectarse (`listo`) el navegador vuelve a pedir avisos y chat: lo que pasó con la conexión cortada no tuvo señal. `CanalEnVivo` (puerto) con `CanalEnMemoria` (un solo servidor; con varios habría que cambiar el adaptador, por ejemplo a LISTEN/NOTIFY). **Cierre de sesión al instante:** todos los caminos que cierran sesiones publican `sesiones.cerradas` con la cuenta y el motivo (`cerrada-por-el-usuario`, `cerrada-desde-otro-dispositivo`, `contrasena-cambiada`, `cuenta-desactivada`; `vencida` al vencer el token) y, después de confirmar, el canal vuelve a validar las conexiones de esa cuenta y corta las que ya no valen. `authMiddleware` deja `req.auth.expiraEn` (del `exp` del token).

**En el navegador** (`client/src/core/tiempoReal/`): la conexión se abre con `fetch` (`EventSource` no deja mandar encabezados) y se reconecta esperando 1, 2, 4… hasta 30 s más un azar. Ante un 401 no reintenta (señal `rechazo`). **Una sola conexión por sesión entre pestañas:** la pestaña que obtiene el candado (Web Locks, `babylon-tiempo-real:<sid>`) la mantiene y reparte por `BroadcastChannel` con el mismo nombre; el `sid` sale del token (`core/lib/token.ts`), así dos cuentas abiertas en el mismo navegador nunca comparten señales. Si el candado llega con la pestaña ya ida (doble montaje de React en desarrollo), se suelta sin conectar. `<TiempoReal />` (en `AppLayout`) refresca la campana con cada señal o al reconectar y, ante `sesion-cerrada`, llama a `irAlLogin(motivo)` (`apiClient.ts`, el mismo camino que un 401). Cerrar sesión en una pestaña avisa a las otras de la misma sesión (`avisarCierreLocal`). La campana ya no consulta cada 5 minutos.

**Criterio único de documentación pendiente** (`documentos/documento.faltantes.ts`): alumno activo e inscripto en el ciclo activo al que le falta cualquiera de los tres documentos (imagen "autorizado", formulario y DNI "cargado"; no tener la fila también es pendiente). Lo usan los avisos, el número del panel (`documentacionPendienteCount`), `GET /api/documentos/faltantes` y el filtro de Alumnos.

**Filtros en la dirección** (`client/src/core/hooks/useFiltrosDeUrl.ts`: `leer`/`escribir`, más `elegir` para validar): pestañas, filtros, página y selecciones viven en `?…`, así un enlace (el de un aviso) los trae puestos y recargar los conserva. Reglas: cambiar un filtro **reemplaza** la entrada del historial ("atrás" lleva a la pantalla anterior); un valor inválido o ajeno cae en el de por defecto (la dirección no da permisos); **nunca** van el texto de un buscador (nombres y DNI de menores) ni lo escrito sin guardar. Tanda 1 hecha: Alumnos (`ciclo`, `cuota`, `curso`, `documentacion`, `datos`, `pagina`), Cuotas (`pestana`), Asistencia (`curso`, `fecha`), Calificaciones (`curso`, `vista`, `evaluacion`, `periodo`) y Mis hijos (`hijo`, con la memoria `ultimoHijoElegido` para que cambiar de pestaña del menú no pierda el hijo). Chats ya tiene la conversación abierta (`conversacion`, subproyecto 3b). **Tanda 2 hecha:** Reportes (`pestana`, `ciclo`, `periodo`), Cursos (`nivel`, `profesor`, `ciclo`; la búsqueda por texto no), Usuarios (`pestana`), Observaciones del profesor (`curso`, `alumno`, `categoria`: un curso ajeno cae en el primero propio, un alumno que no es de ese curso en el primero de la nómina, y lo escrito se descarta al cambiar de alumno) y el legajo (`pestana`, `periodo`, `categoria` de las observaciones). Quedaron fuera a propósito: Profesores (solo tiene un buscador de texto) y el mes del calendario de asistencia del legajo (se calcula solo según los registros).

### Chat en vivo (subproyecto 3b)

- **Bandeja compartida del instituto:** si cualquier cuenta de administración o secretaría lee una conversación, queda leída para todo el instituto.
- **"Leído":** `Mensaje.vistoEn` guarda cuándo lo vio el otro lado (`null` = todavía no). La migración dejó vistos los mensajes que ya existían.
  - `Lector` = `instituto` | `familia`. Leer marca solo los mensajes del otro lado: `rolEmisor` padre para el instituto; admin y secretario para la familia.
- **Regla del "Visto"** (`features/chats/visto.ts`, pura):
  - cada mensaje muestra solo su hora;
  - "Visto · HH:MM" va únicamente debajo del **último** mensaje de la conversación, si es de quien mira y ya fue visto;
  - cuando el otro responde, desaparece; reaparece cuando el otro lea el próximo mensaje propio.
- **Marcar leído solo si alguien mira** (`useMarcarLeidoSiMira`). Se marca solo con la conversación en pantalla, la pestaña visible (`visibilitychange`) y algo del otro lado sin ver.
  - Manda los **ids** de los mensajes sin ver que están en pantalla (no una fecha): uno que llegó en ese instante, aunque tenga la misma fecha o se haya confirmado fuera de orden, no queda leído sin verse. Si hay páginas anteriores sin cargar con algo sin ver, manda también `antesDe` (la fecha del más viejo cargado): abrir la conversación las da por leídas.
  - Si el pedido falla, se reintenta solo (hasta 3 veces, cada vez más espaciado).
- **Mensajes por páginas** (`GET /api/chats/:id/mensajes?antesDe=`): los últimos 50 y, con "Ver mensajes anteriores", los de antes (marcador por fecha e id, como el historial de avisos; inválido → 400). `useMensajes` es un `useInfiniteQuery`: una señal vuelve a pedir solo las páginas cargadas. `useDesplazamientoDelChat` lleva al final con un mensaje nuevo y no hace saltar la vista al cargar los anteriores.
  - El instituto no abre ninguna conversación sola. En el celular, "volver" la cierra (sale de la dirección), así una conversación tapada por la lista nunca se marca.
- **Anuncios** `chat.mensaje` y `chat.leido` (`chats/chat.eventos.ts`, con la cuenta del padre). Se publican dentro de la transacción; leer sin nada pendiente no anuncia.
- **Avisos de estado:**
  - `mensajes_familia` (staff, "N mensajes nuevos de <padre>") y `mensajes_instituto` (padre, "N mensajes nuevos del instituto");
  - clave `mensajes:<chatId>`, recurso `{ tipo: "chat", chatId }`;
  - el nivel = cantidad, así un mensaje más vuelve a "no leído";
  - nunca le llegan a quien escribe.
- **Señal en vivo `chat`** (`{ chatId }`, sin texto; `chats/chat.tiempoReal.ts`): sale al confirmar y va a todas las conexiones de admin/secretaría (`CanalEnVivo.enviarARoles`) y al padre de esa conversación. `<TiempoReal />` invalida `["chats"]` y `["mensajes", chatId]`.
- **Número en el menú lateral** (`ContadorChats`, `NavItem.contador: "chats"`, `GET /api/chats/no-leidos`): conversaciones con algo sin leer para el instituto, mensajes sin leer para el padre.
- **Pantalla Chats:**
  - lista de resúmenes (`GET /api/chats`) ordenada por el último mensaje, con su número de no leídos;
  - la conversación abierta vive en `?conversacion=` (un valor ajeno no abre nada);
  - **"Nueva conversación"** busca padres por nombre, apellido o DNI (el texto no va a la dirección) y llama a `POST /api/chats`. `obtenerOCrear` resiste dos pedidos a la vez: la clave única de `Chat.padreId` hace que el segundo se quede con la del primero. Crear una conversación anuncia `chat.creada` (señal `chat` al instituto: aparece en la lista del resto del equipo). La respuesta trae `estadoCuenta` (`activa`, `inactiva`, `sin-cuenta`): sin cuenta se aclara "Todavía no entró al sistema"; con la cuenta desactivada, que no puede entrar al sistema hasta que se reactive (una cuenta inactiva no puede iniciar sesión).
  - El borrador del mensaje es de su conversación: al cambiar de conversación no se lleva (nunca termina enviado a otra familia).
- **Corregir y eliminar mensajes** (`PATCH`/`DELETE /api/chats/:id/mensajes/:mensajeId`, `ChatService.editarMensaje`/`eliminarMensaje`): la familia solo los suyos; **cualquier cuenta de administración o secretaría, cualquier mensaje del instituto** (no el de la familia); 15 minutos desde el **envío** (`MINUTOS_PARA_CORREGIR`; corregir no renueva el plazo; el server lo controla y el client lo repite en `features/chats/correccion.ts`, `puedeCorregir`). Fuera de plazo → 409; ajeno → 403; mensaje de otra conversación → 404. `Mensaje.editadoEn` ("(editado)") y `eliminadoEn`: **eliminar borra el texto de la base** y queda "Se eliminó este mensaje" (también como último mensaje en la lista del instituto: `ultimoMensaje.eliminado`); eliminar de nuevo no hace nada; el mismo texto no marca "editado". Un corregido conserva su `vistoEn`; un eliminado no lleva "Visto" **y no cuenta como sin leer** (`sinLeer` en `PrismaChatRepository`, el criterio de `mensajes_familia`/`mensajes_instituto` y `noLeidos` del client). Anuncios `chat.editado` y `chat.eliminado` (el segundo re-sincroniza los avisos); la señal en vivo es la misma `chat`. Client: menú "⋯" en `BurbujaMensaje` (Editar en la misma burbuja, Enter guarda y Esc cancela; Eliminar con confirmación), que desaparece solo al vencer el plazo.
- **Pendiente para más adelante:** adjuntos (junto con Documentación, hoy no hay almacenamiento de archivos), avisos por email de mensajes sin leer, historial de versiones de un mensaje corregido.

### Pantallas al día (subproyecto 3c)

**Toda pantalla se actualiza sola** cuando otra persona cambia un dato que muestra, con un resaltado breve y un mensaje "quién hizo qué" ("Lucía cobró la cuota de octubre de Tomás Rodríguez").

- **Quién hizo el pedido:** `core/autoria.ts` (`AsyncLocalStorage`). `authMiddleware` corre el resto del pedido con `ejecutarComo({ usuarioId, rol })`, así ningún service lo recibe por parámetro. Las tareas automáticas (la de las 03:00) no tienen autor: "el sistema".
- **Anuncio `datos.cambiaron`** (`modules/cambios/cambio.eventos.ts`): **toda escritura** lo publica dentro de su transacción con `{ dato, accion, ids, visibleParaFamilias? }` (catálogo en `cambio.entity.ts`: `TipoDato` y `AccionCambio`; solo ids, nunca nombres).
  - Las sesiones no se publican servicio por servicio: el módulo se suscribe a `sesiones.cerradas`.
  - `CuotaRepository.marcarVencidas` devuelve las cuotas marcadas (no la cantidad), para avisar a sus familias.
- **Destinatarios** (`cambio.destinatarios.prisma.ts`, lectura cruzada sobre Prisma, solo cuentas activas). Regla de oro: **una señal nunca le dice a alguien algo que la API no le dejaría leer.**
  - Administración y secretaría reciben casi todo (por rol, con los ids completos); `usuarios` y `profesores` solo el administrador (`GET /api/profesores` es solo suyo); `ciclos`: activar uno le llega a todos, un ciclo nuevo solo a administración, secretaría y profesores.
  - El profesor recibe lo de sus cursos (en una reasignación, el anterior y el nuevo).
  - El padre recibe lo de sus hijos. Cada familia y cada profesor reciben los **ids recortados a lo suyo** (`recortar`: ni ids de otras familias ni cantidades del instituto). **Nada en borrador le llega a las familias:** evaluaciones solo al publicarse, notas solo de evaluaciones publicadas, notas de cierre solo al publicarse.
- **Señal `cambio`** (`cambio.difusion.ts`): sale **después de confirmar** con `{ dato, accion, ids, por: { usuarioId, nombre, rol } | null }`. El autor se toma al publicar (dentro del pedido), no al confirmar.
- **En el navegador** (`features/cambios/`):
  - `core/tiempoReal/senales.ts` reparte las señales sin que core/ conozca a los features.
  - `<CambiosEnVivo />` traduce cada `cambio` en las consultas a volver a pedir (`claves.ts`; TanStack solo recarga las que están en pantalla). Espera 300 ms sin señales, así un lote de cobros es una sola recarga, pero nunca más de 2 s desde la primera (`programador.ts`): con señales que no paran, la pantalla igual se pone al día.
  - Al reconectarse (un `listo` que no es el primero) vuelve a pedir todo lo que está en pantalla.
  - Los cambios ajenos quedan en `core/tiempoReal/cambiosEnVivo.ts` (para el resaltado y los avisos de nómina).
  - `<MensajesDeCambios />` arma el texto con los nombres de la caché (`nombres.ts`, `mensajes.ts`): abajo a la derecha, 5 s, hasta 3. Junta los iguales que llegan dentro de 1 s. No se le muestra a quien hizo el cambio.
- **Resaltado:**
  - `useResaltado` (y `<Resaltable>`; `KpiCard` ya lo trae) ilumina 2,5 s un número que cambió por algo ajeno.
  - `useListaConSalidas` marca las filas nuevas (`fila-entrando`) y deja 1,5 s las que salen (`fila-saliendo`).
  - La primera carga y los cambios propios no se resaltan.
- **Profesor:** la nómina que ve el profesor (`GET /api/cursos/:id/alumnos` pedido por él) tiene **solo alumnos activos**.
  - `useAvisosDeNomina` muestra avisos fijos cuando la nómina cambia mientras la tiene abierta ("Lucía inscribió a Juan Pérez en este curso", "Ana Gómez ya no está en este curso").
  - `useNotasTipeadas` (calificaciones) nunca pisa lo tipeado cuando la lista de lo guardado se vuelve a pedir.
  - `useCursoPerdido` lo deja en el curso que le sacaron, con "Este curso ya no está a tu cargo" y sin poder guardar, en vez de saltar a otro.
- **Observaciones:** muestran autor y rol en el legajo, la pantalla del padre y la del profesor (`etiquetaDeAutor`: "Lucía Peralta · Secretaría"; profesor → "Docente").
- **Cambios sin guardar** (`core/sinGuardar/`):
  - `useSinGuardar(activo)` en cada formulario o pantalla de carga: algo distinto de lo guardado o de cómo se abrió.
  - `<ProteccionSinGuardar />` (con `useBlocker`: **el client usa router de datos**, `createBrowserRouter` en `App.tsx` con el árbol `rutas` de `AppRoutes.tsx`) pregunta "Tenés cambios sin guardar. ¿Salir igual?" ante cualquier cambio de dirección, incluidos los filtros de `?…`. Recargar o cerrar la pestaña muestra el aviso del navegador.
  - `Modal` con `sinGuardar` pregunta antes de cerrar con la cruz.
  - `descartarCambiosSinGuardar()` para las pantallas que guardan y navegan solas.
- **Versión nueva** (`core/version/`):
  - Versión del servidor: `APP_VERSION`, o `dist/version.json` que escribe `pnpm build`, o "desarrollo"; llega en `listo`.
  - Versión del client: `__VERSION_CLIENT__` y `/version.json` publicados por un plugin en `vite.config.ts`.
  - Se comprueba al (re)conectarse y cada 10 min.
  - Si cambió alguna, aparece una franja amarilla que deja terminar ("Hay una versión nueva del sistema. Guardá lo que estés haciendo…", "Recargar ahora").
  - Al guardar algo con éxito (`MutationCache.onSuccess`; las mutaciones con `meta.segundoPlano` no cuentan) aparece el cartel "Recargá para seguir". Ir a otra pantalla recarga la página en esa pantalla, preguntando antes si hay algo sin guardar.

**Limitaciones conocidas:** no hay calendario de feriados (una clase de feriado genera "asistencia sin tomar", que se puede marcar leído y se cierra sola a los 7 días); canal y límites en memoria (un solo servidor).

### Formularios, validación, datos incompletos y responsables (subproyecto 3d)

- **Validación: una regla por tipo de dato, escrita dos veces** (`server/src/core/validacion.ts` y `client/src/core/lib/validacion.ts`, mismos nombres; server y client no comparten código): `recortar`, `normalizarDni` (solo DNI argentino, 7 u 8 dígitos con o sin puntos; se guarda con los dígitos), `normalizarCelular` (celular argentino en las formas habituales; se guarda como `+549` + 10 dígitos), `normalizarEmail`, `fechaNacimientoValida` (fecha real, edad entre 2 y 100 años a hoy), y los esquemas zod `textoRequerido(etiqueta, max)`, `texto(max)`, `textoOpcional(max)`, `dniSchema`, `celularSchema`, `emailSchema`, `fechaNacimientoSchema` más los envoltorios `opcional(…)` (vacío → `undefined`) y `borrable(…)` (vacío o `null` → `null`). `server/tests/casos-validacion.ts` corre la **misma tabla de casos contra las dos copias** (`pnpm test`). **Las notas son solo numéricas** (no hay escala conceptual R/B/MB: se quitó la columna `Evaluacion.escala`): `notaNumericaSchema(minimo)` (solo del server) acepta un número de `minimo` a 10 con hasta dos decimales, con coma o punto, y lo guarda con punto ("7,5" → "7.5"); las evaluaciones admiten desde 0 y la nota de cierre desde 1. Solo del server: `fechaCalendario`, `fechaDeEvaluacionSchema` (entre un año atrás y uno adelante) y `fechaDeAsistenciaSchema` (no futura). Un texto de puros espacios cuenta como vacío y nunca se guarda `""`. Largos máximos: nombre y apellido 60, dirección 150, observaciones 1000, mensaje del chat 2000, nombre de curso/evaluación/categoría 80, aula 30; cupo de 1 a 50; los horarios de un curso no terminan antes de empezar ni se pisan el mismo día (también en `client/src/features/cursos/horarios.ts`, con prueba cruzada contra el esquema del server).
- **Los esquemas de creación y edición son `.strict()`** (un campo desconocido es 400) y todos los módulos pasan por las reglas de arriba. El `errorHandler` responde 400 (no 500) a un cuerpo que no es JSON y suma al detalle de un `ZodError` las claves por ruta completa (`responsable.datos.telefono`) además de las de primer nivel.
- **Editar escribe solo lo que cambió:** `PATCH` distingue "no vino" (no se toca) de `null` (se borra, solo en lo que se puede completar después: DNI, fecha de nacimiento, email, dirección, observaciones, teléfono del alumno, DNI/email/dirección del responsable, aula, teléfono del profesor; lo obligatorio al crear —nombre, apellido, curso, celular y vínculo del responsable— no se puede vaciar y `null` ahí es 400). Los repositorios de `Alumno`, `Padre`, `Profesor` y `Curso` tienen `actualizarParcial(id, Cambios<T>, tx?)` (`Cambios<T>` en `core/ports.ts`; `core/cambios.ts` → `soloPresentes`): dos ediciones de campos distintos no se pisan. `AlumnoRepository`/`PadreRepository.bloquear(id, tx)` (`SELECT … FOR UPDATE`) para lo que toca las dos filas. El DNI de alumnos y responsables se puede corregir (repetido: 409 "Ya existe un alumno/responsable con el DNI …"). Un responsable con cuenta no puede quedar sin email.
- **Datos que pueden faltar y el vínculo en el alumno:** `Alumno.dni`, `Alumno.fechaNacimiento` y `Padre.dni` admiten vacío (únicos cuando están). `Padre.vinculo` **ya no existe**: el vínculo (`padre`, `madre`, `tutor`, `propio`) vive en `Alumno.vinculoResponsable` (el enum de base `VinculoPadre` suma `propio`), porque la misma persona puede ser madre de un alumno y "propio" de otro. "Padre" sigue siendo el nombre en el código; en las pantallas se llama **Responsable**.
- **Alta con lo mínimo:** inscribir exige nombre, apellido, curso y responsable; el responsable nuevo, nombre, apellido y celular (`PadreService.crearFichaEnTransaccion`; el email es solo un dato de contacto: nunca crea una cuenta, eso lo hace el administrador desde "Sin cuenta"). **`propio`** (un adulto responsable de sí mismo): la ficha se arma con sus datos; si ya existe una ficha con su DNI se reutiliza y **manda la ficha** (el alumno toma su nombre; lo escrito solo completa lo que faltaba); un menor de 18 con fecha cargada es 400, y sin fecha de nacimiento solo se admite en un curso de adultos (`adults_*`; es la misma regla que ofrece la pantalla); una ficha tiene a lo sumo un alumno propio; **nombre, apellido y DNI se mantienen iguales entre el alumno y su ficha** (se sincronizan en la misma transacción, bloqueando primero el alumno y después la ficha). `AlumnoService.asignarResponsable` (`PUT /api/alumnos/:id/responsable`) cambia el responsable o el vínculo; el descuento por hermanos se calcula al inscribir y no se recalcula. **Inscribir bloquea la ficha del responsable** (`padreRepo.bloquear`) y rechaza con 409 un alumno activo con el mismo nombre a su cargo (sin mirar mayúsculas ni tildes): así un envío repetido —o dos a la vez— no duplica al alumno ni mide mal el descuento. **Cambiar de responsable avisa también a la familia anterior** (`padreIds` en el anuncio `datos.cambiaron` de `alumnos`, sin el id del alumno que ya no es suyo). El choque de DNI entre dos altas simultáneas (`PrismaAlumnoRepository`/`PrismaPadreRepository.create`) es 409, no 500; `actualizarPadre` y `actualizarProfesor` comprueban con los bloqueos tomados que lo que leyeron sigue igual (si no, 409 "volvé a intentarlo"), y `actualizarProfesor` toma primero el bloqueo de la cuenta y relee la ficha: el nombre de la cuenta sale de lo último guardado. En el client, `SelectorDeResponsable` (existente / nuevo / propio; lo usan Inscribir alumno y "Cambiar responsable") con dos ayudas de la pantalla, no del servidor, que se calculan **mientras se escribe**: `fichasCoincidentes` (`features/padres/fichasParecidas.ts`, pura) avisa si ya hay una ficha con el **mismo DNI, celular o email** (normalizados: puntos, formas de escribir el celular, mayúsculas) y deja solo "Usar esa ficha" —sin "es otra persona": hay que usarla o corregir el dato repetido— y la pasa a "Ya existe en el sistema" con esa ficha elegida; `fichasParecidas` avisa de las parecidas por nombre y apellido y sí obliga a elegir "usar esa ficha" o "es otra persona". Una ficha que coincide por contacto no se repite en las parecidas. El servidor solo rechaza el DNI repetido (409); el celular y el email repetidos los frena la pantalla. En el modo `propio` el celular no se compara (la ficha se reconoce por el DNI del alumno). No hay herramienta para unificar fichas duplicadas: la prevención en la pantalla la reemplaza (las duplicadas que había eran datos de prueba).
- **Datos incompletos:** `datosFaltantes(alumno, responsable)` (`alumnos/alumno.incompleto.ts`, función pura) es el criterio único: `dni`, `fechaNacimiento`, `responsable`, `vinculo`, `responsableDni`, `responsableTelefono`, `responsableEmail` (con `propio` el DNI se informa una sola vez; sin responsable solo se informa eso; no incluye el curso porque la población exige inscripción). Universo: alumno activo inscripto en el ciclo activo (el de la documentación pendiente). Lo usan `GET /api/alumnos/incompletos`, la marca y el filtro `?datos=incompletos` de Alumnos, el cartel del legajo y el aviso de estado `datos_incompletos` (staff, agrupado "Hay N alumnos con datos incompletos"; se sincroniza con `alumnos.cambiaron` y con `datos.cambiaron` de `padres`).
- **Mientras editabas, X cambió…** (`client/src/core/formularios/`): `reconciliar` (pura) y `useFormularioAlDia`: un campo está *tocado* si difiere del último valor que el servidor dijo; los no tocados se actualizan solos (con resaltado) y un aviso fijo dice quién y qué (`textoDelAviso`; la autoría vale 15 s; "alguien"/"el sistema" si no se sabe); lo escrito se conserva sin marcar conflicto. Lo usan Editar datos del legajo, Curso, Profesor y la cuota en Configuración. Al guardar se manda `cambiosParaEnviar` (`core/lib/diferencias.ts`) y las validaciones de la pantalla corren **solo sobre lo modificado** (`resolverSoloModificados` en los formularios de react-hook-form de edición; `EditarDatosModal` a mano): un dato viejo que hoy no cumple las reglas nunca bloquea guardar otro campo. `erroresDeCampo`/`mensajeDeError` reparten el error del servidor (400 por campo, 409 de DNI al campo del DNI).
- **Panel del responsable** (`features/alumnos/modoDelPanel.ts`, `useModoDelPanel`): la misma pantalla, con textos y selector según las cursadas de la cuenta: `hijos` (familia, textos de siempre), `propio` (adulto solo: "Mi cursada", "Mis notas"…, sin selector) o `mixto` (adulto que además es responsable de otros: "Cursadas" y selector con "Yo"). La privacidad no cambia: cada cuenta ve solo a los alumnos de los que es responsable.
- **Pendiente conocido:** el texto legal de autorización de imagen sigue diciendo "padre/madre/tutor" también para un adulto que la firma por sí mismo (es el documento real del instituto: falta su versión para adultos, no se reescribe por cuenta propia).

### Cuotas: generación automática, estados y valor global

**Estados** (`EstadoCuota`): `pendiente` (todavía no venció) → `pagada` (se cobró) o `vencida` (pasó el día 10 sin cobrarse). Nadie marca "vencida" a mano: la tarea periódica lo hace.

**Valor de la cuota**: un único monto global (`Configuracion.valorCuota`, módulo `configuraciones/`, `GET|PATCH /api/configuracion`; el PATCH es solo admin, el GET también secretario). Se edita en Configuración → "Cuota mensual". **Sin valor cargado no se genera ninguna cuota.** Un cambio de valor rige solo para las cuotas que se generen después; las ya generadas conservan su monto. No hay valores por curso ni por nivel (el instituto hoy cobra igual a todos).

**Generación** (`CuotaService`, reglas de calendario puras en `cuotas/cuota.calendario.ts`): una cuota por alumno activo del **ciclo activo** y por mes lectivo (**marzo a noviembre**), solo si el año del ciclo activo coincide con el año actual. Nace `pendiente`, con `montoBase` = valor global y el 10% de descuento si `aplicaDescuentoHermanos`. Vence el **día 10**; si se genera después del 10 de su propio mes (inscripción a mitad de mes, o valor cargado tarde) vence el **último día del mes** para no nacer vencida. `@@unique([alumnoId, mes, anio])` la hace idempotente.
- **Al inscribir** (`AlumnoService.inscribirAlumno`, dentro de la misma transacción): se crea la cuota del mes de inscripción (`generarCuotaInicial`). No hay cuotas retroactivas ni por adelantado.
- **Cada mes, sola** (`cuota.scheduler.ts`, arrancado desde `server.ts`, sobre la tarea diaria compartida `core/tareaDiaria.ts`): al levantar el server y luego **una vez por día a las 03:00 de Argentina** corre `mantenerCuotas()` = `marcarVencidas` (pendiente con vencimiento anterior a hoy → vencida; el propio día 10 todavía se puede pagar) + `generarCuotasDelMes`. No está atada a los días 1 y 11: mira el estado (pendientes ya vencidas, alumnos sin cuota del mes), así que el día 1 crea las del mes, el día 11 marca las vencidas y el resto de los días no cambia nada. Sin cron externo ni dependencia nueva: si el server estuvo apagado en esas fechas, la corrida de arranque lo pone al día. Solo corre mientras el server esté encendido.
- **Hora de Argentina fija en el server** (`core/fechas.ts`, zona `America/Argentina/Buenos_Aires`): todo lo que dependa de "qué día es" (vencimientos, generación mensual, hora de la tarea, "hoy" y "días vencidos" en reportes) usa `fechaHoraEnArgentina()`/`inicioDeHoyUtc()`, nunca `getDate()`/`getMonth()`/`setHours()` locales ni `getUTC*` sobre un instante, para que el resultado no cambie si el servidor se despliega en otra región. Verificado idéntico bajo `TZ=UTC`, `Asia/Tokyo` y `Europe/Madrid`. Argentina no tiene horario de verano; si eso cambiara, `msHastaProximaCorrida` habría que revisarlo. Los `new Date()` que solo guardan un instante (fecha de alta, mensajes, etc.) no necesitan esto.
- Reportes: "al día %" y "tasa de cobranza" se calculan sobre cuotas exigibles (pagadas + vencidas; las pendientes no cuentan). "Deuda"/"Adeuda" = solo vencidas.
- **Ojo al probar**: con un valor cargado y el server corriendo, el scheduler crea cuotas de verdad para los alumnos del ciclo activo, incluidos los de prueba; llevan un id UUID (no `prueba-`), así que `borrar` no las elimina. Dejar `valorCuota` en null (o borrar esas cuotas) al terminar de probar.

### Alta de Secretario: por qué no tiene módulo propio

A diferencia de `Padre` (`dni`, `telefono`) y `Profesor` (`dni`, `telefono`), **`Secretario` no tiene ningún campo propio que no esté ya en `Usuario`** (`nombre`, `email`, `password`) — por eso no existe `modules/secretarios/` ni una entidad `Secretario`: crear un módulo completo (entity+schema+repository+service+controller+routes) para no guardar ningún dato adicional sería ceremonial sin necesidad real. El alta vive directo en `UsuarioService`/`UsuarioController` (montados en `/api/auth`, igual que `login`, porque ese es el módulo que ya posee `Usuario`), simplemente creando un `Usuario` con `roles: ["secretario"]` (`crearCuenta` con ese rol). `listarUsuarios` devuelven `Omit<Usuario, "passwordHash">` — nunca se expone el hash por la API.

### Panel de Usuarios (Admin): cuentas y "Sin cuenta"

`UsuariosPage` (client, solo `admin`) tiene dos pestañas. **Cuentas** es la tabla de las cuentas activas e inactivas (`GET /api/auth/usuarios`: nombre, email, etiqueta(s) de rol —una cuenta multi-rol muestra una por rol—, interruptor de estado, fecha de alta y un lápiz de edición); la cuenta propia no se puede desactivar. **Sin cuenta** (`GET /api/auth/sin-cuenta`) lista a los responsables y profesores activos que todavía no tienen acceso, cada uno con "Crear cuenta" (email de la ficha autocompletado + contraseña). El botón "Crear usuario" sirve para cualquier rol (administrador, secretario, profesor, responsable, varios a la vez): para padre o profesor se elige una ficha sin cuenta o se carga una nueva ahí mismo. Detalle de reglas en "Cuentas: crear y editar". **Regla de diseño que sigue valiendo:** Secretaría no ve este panel (su alcance son los legajos); da de alta responsables y alumnos *sin cuenta* desde Inscribir alumno.

El rol se valida con `requireRole` a nivel de ruta; la propiedad sobre el recurso puntual (¿es tu curso?, ¿es tu hijo?) se valida dentro del service y devuelve `AuthorizationError` (403). El `errorHandler` también traduce `ZodError` (validación de body) a 400 automáticamente.

**Listados con alcance distinto según el rol** (ej. `GET /api/cursos`): cuando varios roles comparten una misma ruta pero cada uno debe ver un subconjunto distinto (profesor → solo sus cursos; admin/secretario → todos), la rama por rol vive en el **controller** (`if (req.auth!.rol === "profesor") { ... }`), no en el service ni en middleware — el service expone métodos separados (`listarCursos()` vs `listarPorProfesor(id)`) y el controller decide cuál llamar según `req.auth`. Mismo patrón a reutilizar en `calificaciones` (borrador oculto a Padre) y `chats` (padre ve solo su conversación).

`container.ts` siembra 4 usuarios de desarrollo (uno por rol, cada uno con su `Padre`/`Profesor` real vinculado por `usuarioId` cuando corresponde) más un curso/alumno/cuota de ejemplo, para poder probar la API sin depender de un flujo de onboarding real: `admin@babylon.test` / `secretario@babylon.test` / `profesor@babylon.test` / `padre@babylon.test`, todos con contraseña `"<rol>1234"`. Esto se reemplaza por `prisma/seed.ts` cuando los repositorios pasen a ser Prisma.

## Client — piezas base (FASE 4)

- **UI**: los componentes de `core/components/ui/` (`button`, `input`, `label`, `card`, `table`, `badge`, `select`, `avatar`, `interruptor`) están escritos a mano siguiendo el patrón estándar de shadcn/ui (CVA + `cn()`), **no generados por el CLI** — el CLI (`pnpm dlx shadcn@latest`) se cuelga en este entorno de desarrollo (sin acceso de red confiable para su registro). Si en el futuro el CLI funciona, se puede usar para agregar componentes nuevos; los ya escritos a mano son compatibles con su formato.
- **Sesión**: `core/store/sessionStore.ts` (Zustand + `persist` en localStorage, key `babylon-session`) guarda `{ token, usuario }`. `core/lib/apiClient.ts` es un wrapper de `fetch` (`get`/`post`/`patch`/`delete`) que agrega el header `Authorization` automáticamente desde el store y traduce respuestas de error del backend a `ApiError`.
- **Mi cuenta** (`/mi-cuenta`, todos los roles, enlace en el bloque nombre+rol al pie del menú; `features/cuenta/`): datos de la sesión (con la leyenda "Para cambiar tu contraseña o tu email, pedíselo a la administración") y sesiones activas (dispositivo, IP, inicio, último uso ± 5 min; cerrar una o todas las demás) y la sección "Notificaciones" (qué tipos de aviso aparecen en la campana, por rol). `logout()` avisa al servidor (si falla, igual cierra localmente).
- **Rutas**: router de datos (`createBrowserRouter` en `App.tsx`, desde el árbol `rutas` de `core/routes/AppRoutes.tsx`; hace falta para `useBlocker`, ver "Pantallas al día") + `ProtectedRoute.tsx` (redirige a `/login` si no hay sesión, o a `/dashboard` si el rol no está en `rolesPermitidos`). `core/components/layout/AppLayout.tsx` es el shell autenticado (sidebar + header, ver "Sistema de diseño" más abajo) que envuelve las rutas protegidas.
- **`Rol`/`Usuario` están duplicados entre server y client** (`server/src/core/ports.ts` vs `client/src/features/auth/types.ts`) — es intencional: server y client no comparten código (ver arriba), así que cualquier cambio a la forma de estos tipos hay que replicarlo a mano en los dos lados.
- **Dashboard por rol**: `features/dashboard/pages/DashboardPage.tsx` elige qué renderizar según `usuario.rol`. Solo `admin` y `secretario` tienen una pantalla de "resumen" propia (`AdminDashboard`/`SecretarioDashboard`, con contenido real); `profesor` y `padre` no la tienen — ni en el prototipo ni acá — así que `DashboardPage` los redirige directo a su primera pantalla real (`/cursos` y `/mis-hijos` respectivamente, ver "Pasada de fidelidad completa" más abajo).
- **`AlumnoService` depende de `CursoRepository`** (además de `AlumnoRepository`) para `listarPorCurso(cursoId, profesorId?)` — cuando `profesorId` viene informado (lo llama un profesor), valida que sea dueño del curso antes de devolver la nómina; si no viene (lo llama admin/secretario), no valida nada. Mismo patrón de "parámetro opcional = viene de un profesor" que ya se usaba en otros services.
- **`useTomarAsistencia` (client) llama a `POST /api/asistencia/masiva`, un único POST atómico** — no dispara un request por alumno. `CursoDetailPage` muestra un solo mensaje de éxito/error para toda la nómina (ver nota sobre `AsistenciaService.registrarAsistenciaMasiva` en la sección de `UnitOfWork`).
- **`features/padres/` no estaba en el scaffolding original de FASE 0** (quedó afuera de la lista de features del client por un descuido) — se creó recién al construir el flujo de Secretario, con la misma estructura que el resto (`types.ts`, `padreService.ts`, `hooks/`).
- **`core/components/ui/select.tsx`**: un `<select>` nativo estilado igual que el resto de los componentes ui (sin Radix) — alcanza para los desplegables simples del proyecto (vínculo del padre, método de pago, nivel de curso) sin sumar una dependencia nueva.
- **Patrón "crear entidad relacionada embebida en el mismo formulario"**: `InscribirAlumnoPage.tsx` usa **dos** instancias de `useForm` (una para el alumno, otra para el padre nuevo) dentro de un único `<form>` — si el usuario elige "Cargar nuevo" padre en vez de buscar uno existente, al enviar el formulario del alumno se valida y crea primero el padre (`padreForm.trigger()` + `crearPadre.mutateAsync(...)`), y recién con ese `padreId` se llama a `inscribirAlumno`. Mismo patrón a reutilizar en cualquier otro flujo donde haga falta crear una entidad relacionada al vuelo (ej. crear un curso nuevo desde el mismo formulario de otra pantalla).

### Regla de diseño: mismo permiso de backend, distinta puerta de entrada en la UI

`POST /api/padres` acepta tanto `admin` como `secretario` (ver tabla de API arriba), pero **eso no significa que ambos vean la misma pantalla**. Es una decisión de UI, no de permisos:

- **Admin** ve un panel general de "Usuarios" (coincide con que el spec original lista "usuarios" dentro del acceso total de Administrador) para gestionar cualquier tipo de cuenta — padres, profesores, secretarios.
- **Secretario** no tiene acceso a ese panel general. Ve la opción de "crear padre/tutor" **embebida dentro del flujo de inscribir un alumno** (si el padre todavía no existe al inscribir, hay un sub-formulario ahí mismo) — coherente con que su alcance es "legajos de alumnos", no gestión de usuarios en general.

Mismo endpoint, mismo `PadreService.crearPadre` por debajo — la diferencia es exclusivamente desde qué pantalla cada rol llega a usarlo. Tenerlo en cuenta al construir el client de `padres` y el panel de Admin: **no exponer un panel de "Usuarios" genérico para el rol Secretario.**

## Sistema de diseño (2026-07-31, portado de `referencia-prototipo/`)

El cliente pasó de un tema shadcn genérico (azul) a la identidad visual real del instituto: `referencia-prototipo/` (en la raíz del repo, fuera de `server/`/`client/`) contiene un prototipo estático (React+Babel por CDN, sin build) con el diseño que el cliente real aprobó — sidebar oscuro verde institucional, hairline borders, esquinas afiladas, tipografía Inter Tight. **Esa carpeta es solo referencia de diseño, no se ejecuta ni se importa desde el client real** (no tiene TypeScript, no tiene build, y sus datos son mock). Ojo: ese prototipo no puede abrirse en este sandbox (usa CDNs externos — React/Babel/Tailwind/Google Fonts/lucide por `unpkg.com` — y acá no hay salida a internet), así que la fidelidad se logró leyendo el código fuente (`babylon-tokens.css`, `babylon-layout.jsx`, etc.), no renderizándolo.

**Decisión clave — "puente de tokens" en vez de reescribir cada página**: en lugar de tocar los ~30 archivos de página que ya usaban clases Tailwind tipo `bg-accent`/`text-muted-foreground`/`border`/`text-destructive`, se remapearon los **mismos nombres de variable CSS que ya consumía todo el client** (`--background`, `--primary`, `--muted`, `--accent`, `--destructive`, `--border`, `--radius`, en `client/src/index.css`) a la paleta hex del prototipo convertida a HSL. Resultado: **todas las páginas ya construidas heredaron el nuevo look automáticamente**, sin editarlas una por una — mismo principio de apalancamiento que ya se usó para roles/errores, aplicado esta vez a estilos. Además de ese puente, `index.css` suma los tokens propios del prototipo en hex crudo (`--brand`, `--sidebar-bg`, `--success`/`--warning`/`--danger` + variantes `-soft`, `--level-*`) y sus clases utilitarias calcadas del original (`.btn-*`, `.card-hl`, `.status`, `.tag`, `.level-pill`, `.nav-link`, `.avatar`, `.tbl`, etc.) para componentes nuevos que sí necesiten fidelidad 1:1.

- **Tipografía**: Inter Tight (+ JetBrains Mono para números/datos) vía Google Fonts (`link` en `index.html`) — variable `--font-sans` en el bloque `@theme` de `client/src/index.css` y `index.css`. Como Google Fonts requiere red, en este sandbox (sin internet) el navegador cae al fallback `system-ui`; en producción con internet real carga Inter Tight normalmente. No es un bug, es una limitación del entorno de verificación.
- **`AppLayout.tsx`** se reescribió por completo: sidebar fijo verde institucional (`var(--sidebar-bg)`) con navegación agrupada por rol (`core/components/layout/nav.ts`, función `navPorRol(rol)` — un array de grupos con label + ítems `{to, label, icon}` de `lucide-react`), pie con avatar + nombre + rol + logout, y drawer móvil equivalente. **El header superior (2026-08-01) ya no es minimal**: `core/components/layout/pageTitles.ts` (`obtenerTituloPagina(pathname)`, match por prefijo de ruta más largo) muestra título+subtítulo real de la pantalla actual (mismo criterio que `SCREEN_TITLES` del prototipo, adaptado de screen-id a ruta de React Router), y `core/components/layout/GlobalSearch.tsx` agrega una búsqueda global **real** (no decorativa): busca alumnos por nombre/DNI usando `useAlumnos()` (ya cacheado por TanStack Query) y navega a `/alumnos/:id` al elegir un resultado — solo se renderiza para `admin`/`secretario` (únicos roles con acceso a ese endpoint y a esa pantalla). ## Pasada de fidelidad completa con el prototipo (2026-08-01)

A pedido explícito del usuario ("quiero que el proyecto real sea igual que en el prototipo… absolutamente todo"), se rehicieron **todas** las pantallas de los 4 roles pantalla por pantalla contra `referencia-prototipo/babylon-{admin,teacher,parent,chat}.jsx`, con la regla ya vigente de no inventar datos: cuando el prototipo mostraba un KPI o vista agregada que el backend no calculaba, se construyó el endpoint real correspondiente en vez de simularlo. Cambios de fondo (no solo visuales):

- **`modules/reportes/` (server, nuevo, sin entidad propia)**: igual criterio que "Alta de Secretario" — es una composición de lectura sobre otros módulos, no un agregado de dominio, así que `ReporteService` consulta Prisma directo en vez de pasar por cada repository. Dos métodos: `obtenerResumenDashboard()` (KPIs de `AdminDashboard`/`SecretarioDashboard`) y `listarReporteAlumnos()` (fila por alumno para las 3 pestañas de `ReportesPage`). Montado en `/api/reportes`, `admin`+`secretario` únicamente.
- **Layout de ancho completo**: `AppLayout.tsx` tenía `max-w-[1400px] mx-auto` en el contenedor principal, dejando franjas vacías en pantallas anchas — se quitó; el contenido ahora ocupa todo el ancho disponible en todas las pantallas.
- **Padre — restructurado a un único componente con tabs, no páginas separadas**: el prototipo (`ParentHome`) es en realidad **una sola pantalla con `tab` interno** (`home`/`grades`/`attendance`/`fees`/`docs`) que cambia según qué ítem de nav se clickeó — no una pantalla por hijo con sub-rutas. `features/alumnos/pages/ParentDashboardPage.tsx` reemplaza a los extintos `MisHijosPage`+`HijoDetailPage`: un solo componente, selector de hijo por segmented-control (si hay más de uno), header con 3 stats reales (promedio/asistencia/cuota actual) y tabs Resumen/Notas/Asistencia/Cuotas/Docs. `nav.ts` (`NAV_PADRE`) pasó de 2 ítems a 6 (`/mis-hijos`, `/mis-hijos/calificaciones`, `/mis-hijos/asistencia`, `/mis-hijos/cuotas`, `/mis-hijos/documentacion`, `/chat`), todas montadas sobre el mismo componente — `pathname` decide el tab inicial (`tabIdDesdeRuta` en el propio archivo). `DashboardPage` ahora redirige `padre`→`/mis-hijos` directo (no hay pantalla de "resumen" genérica para este rol, coincide con que el prototipo tampoco la tiene).
- **Profesor — mismo criterio, restructurado a 4 pantallas con selector de curso en vez de rutas por `:id`**: el prototipo tampoco navega a un curso por URL — cada pantalla (`TeacherAttendance`/`TeacherGrades`/`TeacherObservations`) tiene su propio `<select>` de curso arriba. Se eliminaron `CursoDetailPage`, `EvaluacionesPage`, `CargarNotasPage`, `NotasCierrePage` y `ObservacionesAlumnoPage`; reemplazados por `AsistenciaProfesorPage`, `CalificacionesProfesorPage` (con vista interna Evaluaciones/Notas de cierre) y `ObservacionesProfesorPage`, todas con selector de curso propio. `MisCursosPage` (Home) quedó como landing real con KPIs (comisiones a cargo, alumnos totales, próxima clase — calculada de verdad proyectando `Horario.diaSemana`+`horaInicio` al próximo día que corresponda) y panel de "Próximas clases". `nav.ts` (`NAV_PROFESOR`) pasó de 1 ítem a 4 (`/cursos`, `/asistencia`, `/calificaciones`, `/observaciones`), rutas ahora `rolesPermitidos={["profesor"]}` (antes compartían `/cursos` con admin/secretario sin necesidad real). `DashboardPage` redirige `profesor`→`/cursos`.
- **Asistencia de Profesor**: tarjetas por alumno con botones Presente/Tarde/Ausente (en vez del `<select>` viejo), conteo real de "ausencias en el mes" por alumno (`useQueries` sobre `GET /api/asistencia/alumnos/:id`, uno por alumno de la nómina — aceptable en un instituto de ~130 alumnos, cursos de ≤30). Sigue sin existir un selector de "clase anterior" con historial completo como el prototipo (`pastSessionsFor`) — se mantiene un `<input type="date">` libre en su lugar; es una reducción de alcance honesta, no fabricada.
- **Calificaciones de Profesor**: fusiona Evaluaciones (chips por evaluación, filtro por período, modal "Nueva evaluación", stats promedio/cargadas/≥7) y Notas de cierre (selector Julio/Noviembre, publicar con modal de confirmación) en una sola pantalla con toggle interno, igual que `TeacherGrades` del prototipo. Nuevo endpoint `GET /api/calificaciones/cursos/:cursoId/notas-cierre?periodo=` (`CalificacionRepository.findNotasCierreByCursoId`) para traer las notas de **toda la nómina** de una — antes solo existía "por alumno". El flujo de publicar guarda primero lo tipeado en pantalla y publica con los ids que devuelve ese guardado (no con `notasExistentes`, que podría estar desactualizado si el profesor no clickeó "Guardar" antes).
- **`CalificacionService.listarCalificacionesDeAlumno` ahora devuelve `CalificacionConEvaluacion`** (nota + `evaluacionNombre`/`evaluacionTipo`/`evaluacionFecha`/`evaluacionPeriodo`, resuelto en el service) en vez de la `Calificacion` pelada — la necesitaba tanto `ParentDashboardPage` como el tab "Académico" de `AlumnoDetailPage` (legajo de Admin) para mostrar qué evaluación es cada nota, no solo el número.
- **Cuotas — Admin/Secretario reconstruida por completo**: tabs Vencidas/Pendientes/Cobradas/Todas con contadores reales, 4 KPIs (cobrado este mes, deuda total, pendientes, tasa de cobranza), modal de cobro multi-cuota con búsqueda de alumno. Nuevos endpoints `GET /api/cuotas/pagos` (todos los pagos, para el historial "pagada el · método" y el KPI mensual) y **`GET /api/cuotas/alumnos/:alumnoId` ahora también acepta rol `padre`** (antes admin/secretario únicamente — el padre no podía ver ni siquiera sus propias cuotas; mismo patrón `Solicitante`/`verificarAccesoAlAlumno` que ya usaban `asistencia`/`calificaciones`/`observaciones`).
- **Cursos — Admin reconstruida por completo**: filtros (nombre/profesor, nivel, profesor), tabla con horarios y cupo real, modal de alta/edición compartido, toggle rápido de estado, vista "Ver alumnos" (nómina + cuota + asistencia, anidada en la misma página, sin ruta propia). Nuevos endpoints `PATCH /api/cursos/:id` (edición parcial, admin) y `GET /api/cursos/horarios` (todos los horarios, join client-side — antes los horarios se guardaban al crear un curso pero **nunca se leían de vuelta en ningún lado**, ni siquiera para el profesor).
- **Chats — unificados a una sola pantalla master-detail por rol** (antes `ChatsAdminPage` listaba y `ChatAdminDetailPage` (ruta separada) mostraba la conversación): `ChatsAdminPage.tsx` ahora es un layout de dos paneles en una sola página (lista de conversaciones a la izquierda con último mensaje y nombre de los hijos, conversación a la derecha), igual que `StaffChat` del prototipo. `ChatPage.tsx` (padre) rediseñado con burbujas alineadas por emisor. Desde el subproyecto 3b existe `Mensaje.vistoEn`: la lista muestra los no leídos de cada conversación (ver "Chat en vivo").
- **Bug recurrente encontrado dos veces — UTC vs. huso horario local**: el entorno corre en GMT-3; `new Date().toISOString().slice(0,10)` (o cualquier cómputo de "hoy" pasando por UTC) se corre un día hacia adelante en las últimas ~3 horas de cada día local. Apareció primero en `ReporteService` (una evaluación de "hoy" quedaba excluida de "Próximas evaluaciones", arreglado con `inicioDeHoyUtc()` — comparación en UTC consistente en ambos lados) y de nuevo en el client (`AsistenciaProfesorPage`/`CalificacionesProfesorPage` proponían "mañana" como fecha por defecto). Fix client-side centralizado en `core/lib/utils.ts` → `hoyLocalISO()` (arma el string `AAAA-MM-DD` a mano con `getFullYear()`/`getMonth()`/`getDate()` locales, nunca `toISOString()`) — **usar siempre esta función para "la fecha de hoy" en un `<input type="date">` o similar**, nunca `new Date().toISOString()`.
